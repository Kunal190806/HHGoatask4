# Blog Post Outline: Agentic Fraud Investigation with TigerGraph

## 1. The Problem
- The sheer volume of false positives generated by traditional risk scoring models.
- Human analysts waste 80% of their time manually querying disconnected systems to gather context.

## 2. Why Graph Databases Matter for Fraud
- Fraud isn't an isolated event; it's a network.
- Discuss how out-of-the-box relational queries struggle with multi-hop relationships (e.g., finding all cards linked to a device that was linked to a previous fraud case).
- Introduce TigerGraph's GSQL for deep traversal.

## 3. Architecture: The Agentic Investigation Loop
- Show the separation of concerns: The LLM is **not** the fraud detector.
- TigerGraph is the **Evidence Engine**.
- The Agent Orchestrator runs the loop: `Trigger -> Graph Tools -> Policy -> Uncertainty Check -> Action`.

## 4. TigerGraph MCP (Model Context Protocol)
- Explain how we securely exposed GSQL queries to the LangGraph agent using strict JSON schema boundaries.

## 5. GraphRAG & Case Memory
- How we replaced static rulebooks with Vector Retrieval for policies.
- **Case Memory**: Explaining how writing finished cases back into the graph allows the agent to find similar historical fraud patterns on the next run.

## 6. Handling Uncertainty
- Discussing why agents must know when they *don't* have enough evidence.
- Our implementation of Policy R1: Pausing the agent loop to request simulated Step-Up Authentication before making a final block decision.

## 7. Results and Benchmarking
- Summarize the performance of the agent against the 20 benchmark cases.
- Explain the `Next Best Action` matrix (Allow, Monitor, Block, Report).

## 8. Lessons Learned & Future Improvements
- Combining transactional GSQL features with LLM reasoning.
- Next steps: Real-time Kafka ingestion and streaming agent pipelines.
